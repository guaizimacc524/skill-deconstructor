## 1. 分析前提

拆解不是复述功能说明，而是从最终交付反向重建设计逻辑。分析始终围绕三个层次：

- **观察层**：Skill 实际写了什么、引用了什么、要求做什么。
- **解释层**：这些设计如何共同产生交付，为什么采用这一顺序和分工。
- **抽象层**：去掉具体工具和任务后，哪些原则能迁移到新问题。

先区分目标环境与通用设计。某项设计只在特定平台成立时，不把它写成普遍要求。

## 2. 第零步：建立 Skill 全景地图

### 要回答的问题

- 分析范围是单文件、完整目录还是带运行证据的 Skill？
- 名称和描述声明了什么能力、触发时机和排除边界？
- 主体、引用、脚本、资产、UI 元数据和外部工具分别承担什么作用？
- 哪些文件被显式引用，哪些存在但没有调用路径？
- 哪些依赖缺失、不可访问或只在某种环境可用？

### 必需产物

建立文件与依赖表：

| 资源 | 类型 | 声明用途 | 读取/调用时机 | 核心路径所需 | 状态 | 证据 |
|---|---|---|---|---|---|---|

状态使用：`存在`、`缺失`、`未引用`、`不可访问`、`条件使用`、`未知`。

再给出范围说明：已读内容、未读内容、未运行内容、目标环境和由此造成的分析限制。

### 注意

- 不把“目录里有文件”误认为“流程会使用该文件”。
- 不要求每个 Skill 都有引用、脚本或资产。
- 资产内容只有在决定输出结构或质量时才需要深入检查。

## 3. 第一步：看交付

### 目标

确定 Skill 的评价终点。忽略“能写文案”“能分析数据”等宽泛介绍，找到实际输入、交付物和完成条件。

### 分析问题

- 谁发起任务，典型请求是什么？
- 必需输入、可选输入和环境前提是什么？
- 最终交付是对话、文件、判断、外部状态变更，还是它们的组合？
- 交付对象是谁，如何被消费或继续执行？
- 什么条件下算完成？谁拥有最终判定权？
- 有无失败、暂停、部分完成或降级交付？

### 必需产物

先写成一句话：

> 这个 Skill 把【输入】转化为【结果】，为【对象】解决【问题】；当【完成条件】成立并由【责任人/机制】确认时完成。

再建立交付契约：

| 项目 | 内容 | 必需/可选 | 证据 | 状态 |
|---|---|---|---|---|
| 输入 |  |  |  |  |
| 输出 |  |  |  |  |
| 完成条件 |  |  |  |  |
| 非成功终态 |  |  |  |  |

完成条件缺失时标为未知，不用常识替作者补全。

## 4. 第二步：看动作

### 目标

把模糊叙述改写为可以从文件或运行行为观察到的动作链。

### 动作分类

- 读取：文件、参数、上下文、外部事实。
- 判断：分类、比较、选择、批准、拒绝。
- 转换：计算、解析、格式化、归一化。
- 生成：文本、代码、文件、计划、建议。
- 调用：脚本、工具、MCP、子智能体、外部服务。
- 检查：结构、内容、格式、安全、完成条件。
- 控制：分支、跳过、重试、回退、停止、降级。
- 交付：返回、保存、发送、提交或等待确认。

### 方法

1. 提取动词和动作对象。
2. 把“全面分析”“妥善处理”等不可观察表述拆成具体行为。
3. 补齐材料中明确存在的条件分支、异常路径、验证和停止动作。
4. 合并不改变控制逻辑的细碎动作。
5. 标注每一步的输入、输出和证据。

### 必需产物

写出简明动作链：

```text
读取 A → 验证 B → 判断 C → 生成 D → 检查 E → 交付 F
```

再建立动作明细：

| 编号 | 可观察动作 | 输入 | 产物/状态变化 | 分支或失败路径 | 证据 |
|---|---|---|---|---|---|

## 5. 第三步：看顺序

### 目标

从“步骤先后”继续追问到“因果依赖”。

### 逐步追问

- 下一步需要使用这一步产生的什么信息或状态？
- 如果交换两步，结果会失败、降质、失控，还是基本不变？
- 如果删除这一步，哪个风险会出现？
- 该顺序是硬性要求、质量偏好、安全保护，还是作者习惯？
- 是否存在可并行步骤？Skill 为何选择串行或并行？

### 依赖类型

- **数据依赖**：后一步需要前一步的产物。
- **评价依赖**：必须先建立标准，才能生成或选择。
- **安全依赖**：必须先检查或授权，才能产生副作用。
- **资源依赖**：只有满足条件才加载昂贵或稀缺资源。
- **反馈依赖**：验证结果决定重试、修复或停止。
- **习惯顺序**：未发现明确因果，不能伪装成必然要求。

### 必需产物

建立因果表：

| 前置动作 | 后续动作 | 依赖类型 | 为什么必须这样排序 | 交换/删除的影响 | 证据性质 |
|---|---|---|---|---|---|

最后将关键路径改写为：

> 因为【要解决的问题/避免的风险】，所以必须先【前置动作】，再【后续动作】。

## 6. 第四步：看分工

### 目标

说明谁做什么、依据什么、产生什么，以及谁对最终结果负责。

### 责任角色

- **AI**：理解语义、比较方案、权衡和解释。
- **脚本**：确定性计算、重复转换、格式生成和机械验证。
- **工具/MCP**：文件操作、执行能力、连接外部系统。
- **外部资料**：提供 Skill 本身没有的新事实、标准或数据。
- **人**：提供目标、授权高风险动作、处理价值取舍和最终验收。
- **运行平台**：提供权限、隔离、上下文加载和依赖环境。

这些是分析类别，不是固定答案。评价的是分工是否适合任务的确定性、风险和成本。

### 必需产物

| 动作 | 执行者 | 判断/执行依据 | 输入 | 输出 | 失败时谁处理 | 最终负责者 | 证据 |
|---|---|---|---|---|---|---|---|

重点检查：

- 是否让 AI 重复完成本可由脚本可靠执行的确定性操作？
- 是否让脚本承担本需语义判断或价值取舍的工作？
- 是否把工具能力误写成 Skill 自身能力？
- 是否有高风险动作缺少人的授权？
- 是否存在责任真空：流程失败后无人决定如何继续？

## 7. 第五步：看约束

### 目标

从“必须、不要、只能、检查、失败即停止”等规则中恢复作者试图防范的风险。

### 方法

1. 提取强制、禁止、限制、验证、重试和停止语句。
2. 说明规则保护的对象和适用阶段。
3. 反事实追问：没有该规则，最可能出现什么失败？
4. 区分安全约束、质量约束、兼容约束和偏好。
5. 检查约束是否有执行机制；只有口号而无检查时标明弱控制。

### 必需产物

| ID | 风险 | 触发条件 | 规则/门禁 | 防护机制 | 失败表现 | 失败后行为 | 证据 |
|---|---|---|---|---|---|---|---|

真正的门禁必须改变控制流：未通过时会暂停、停止、请求补充、回退、重试或降级。普通建议和一般检查不能都标成门禁。

## 8. 第六步：看原则

### 目标

去掉工具名、文件名、平台名和当前任务名，提炼可迁移的判断。

### 原则模板

> 当【适用条件】时，应【动作】，因为【理由/所防风险】。这条原则成立的前提是【前提】，不适用于【边界或反例】。

### 五项检验

1. **去具体化**：删掉专有名词后仍然成立吗？
2. **跨任务迁移**：换到另一个领域仍能指导决策吗？
3. **证据追溯**：能指出原 Skill 中支持它的设计吗？
4. **前提检查**：原则依赖什么环境、能力或输入？
5. **反例检查**：在哪些情况下不应采用它？

未通过检验的内容只能称为局部做法或作者偏好，不写成通用原则。

### 必需产物

| 原则 | 条件 | 动作 | 理由/风险 | 成立前提 | 边界/反例 | 原设计证据 | 可迁移场景 |
|---|---|---|---|---|---|---|---|

不要强迫残缺或平庸的 Skill 产出深刻原则。证据不足时可以得出“尚无可靠可迁移原则”。

## 9. 证据追溯与迁移出口

### 证据追溯矩阵

为决定总评和核心原则的结论建立追溯矩阵：

| 结论 ID | 结论 | 类型 | 来源位置 | 支撑强度 | 影响的评分/原则 |
|---|---|---|---|---|---|

来源优先写成 `相对路径 > 标题`，能取得稳定行号时写成 `相对路径:行号`。运行证据注明测试输入、环境和实际结果。

### 迁移出口

学习型报告的最终价值不是立即重写原 Skill，而是给未来设计提供可复用判断。最后总结：

- 最值得借鉴的三项设计选择；
- 只适用于当前任务的局部做法；
- 可以迁移到新 Skill 的原则；
- 迁移时必须重新确认的前提；
- 如果未来创建新 Skill，应该先收集哪些真实请求和失败案例。

除非用户要求，不输出新 Skill 的实现方案或修改补丁。
