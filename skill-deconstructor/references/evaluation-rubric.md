# Skill 量化测评规则

## 1. 测评模型

同时报告三个互不替代的结果：

1. **设计质量总分（0～100）**：Skill 的静态设计质量。
2. **关键质量门禁**：是否存在即使总分较高也会阻止安全、可靠使用的问题。
3. **证据置信度（0～100%）**：分析结论得到多少直接文件或运行证据支持。

不要把静态高分写成“运行可靠”或“生产可用”。只有经过目标环境中的真实请求、反例和异常输入验证，才能对运行表现作出相应判断。

## 2. 通用评分锚点

每个评分项先按 0～4 评级，再换算为该项分数。

| 评级 | 判断锚点 |
|---:|---|
| 0 | 缺失、无效、核心引用断裂，或存在直接冲突 |
| 1 | 有所提及但模糊，难以执行或只剩口号 |
| 2 | 基本存在，只覆盖理想路径或依赖大量临场猜测 |
| 3 | 清晰可用，覆盖主要路径，存在少量非关键缺口 |
| 4 | 明确、完整、与风险匹配，并在适用时具有验证证据 |

单项换算：

```text
单项得分 = 单项满分 × 评级 ÷ 4
```

最终总分保留到 0.5 分。不要制造小数点后多位的虚假精度。

## 3. 评分维度与子项

### A. 任务价值与范围边界（10 分）

| ID | 子项 | 满分 | 评价重点 |
|---|---|---:|---|
| A1 | Skill 化的必要性 | 3 | 是否服务真实、可重复、需要稳定方法或专业知识的任务 |
| A2 | 用户、问题与对象 | 3 | 谁使用、解决什么问题、处理什么对象是否明确 |
| A3 | 范围、排除与组合边界 | 4 | 是否避免万能化，能否与相似 Skill 或工具区分 |

不要因为任务简单而扣分；只在普通提示即可稳定完成、Skill 没有带来可复用知识时降低 A1。

### B. 发现与触发设计（15 分）

| ID | 子项 | 满分 | 评价重点 |
|---|---|---:|---|
| B1 | 名称 | 2 | 清晰、符合约定、体现动作或任务、不过度冲突 |
| B2 | 描述 | 4 | 同时说明“做什么”和“何时使用” |
| B3 | 正向触发 | 3 | 典型匹配请求能被描述覆盖 |
| B4 | 负向边界 | 4 | 相近但不匹配请求、类似 Skill 和误触发风险得到区分 |
| B5 | 元数据一致性 | 2 | UI 元数据、默认提示和调用策略与 Skill 本体一致 |

没有明确正反例不必自动给 0 分；根据描述能否可靠区分请求评分。若有真实触发测试，则提高证据置信度。B5 在目标规范或运行环境不使用独立 UI 元数据时可标为 `N/A`；不要为了得分要求增加可选配置文件。

### C. 交付契约（10 分）

| ID | 子项 | 满分 | 评价重点 |
|---|---|---:|---|
| C1 | 输入要求 | 3 | 必需、可选输入和前提是否明确 |
| C2 | 输出与格式 | 3 | 最终交付物、结构、保存或返回方式是否明确 |
| C3 | 完成条件与验收者 | 4 | 如何判断完成、失败或部分完成，最终由谁确认 |

### D. 工作流与控制逻辑（20 分）

| ID | 子项 | 满分 | 评价重点 |
|---|---|---:|---|
| D1 | 动作可执行性 | 5 | 步骤是否具体、可观察、可由当前能力完成 |
| D2 | 顺序与依赖 | 3 | 关键先后是否符合数据、评价、安全或资源依赖 |
| D3 | 分支与跳过条件 | 4 | 条件路径、模式选择和可选步骤是否明确 |
| D4 | 缺失与异常处理 | 3 | 缺字段、错误格式、依赖不可用时如何处理 |
| D5 | 门禁、循环与停止 | 3 | 何时确认、重试、回退、暂停、失败或降级 |
| D6 | 结果验证动作 | 2 | 交付前是否实际检查结构、内容或关键不变量 |

不要把创意任务缺少唯一顺序视为缺陷；评价它是否保留了合适自由度，同时守住必要标准。

### E. 分工与资源架构（15 分）

| ID | 子项 | 满分 | 评价重点 |
|---|---|---:|---|
| E1 | AI 与确定性逻辑分工 | 4 | 理解取舍交给 AI，重复计算和转换在必要时脚本化 |
| E2 | 工具与外部能力 | 3 | 能力、权限、MCP 或外部数据依赖是否真实且说明清楚 |
| E3 | 文件职责与加载时机 | 4 | 主体、引用、脚本、资产各司其职，调用时机明确 |
| E4 | 人与最终责任 | 2 | 目标判断、高风险授权和最终验收责任是否合理 |
| E5 | 复杂度与可组合性 | 2 | 没有无必要的大而全结构，适合拆分时能组合 |

不要求存在脚本、引用或资产；不存在但不需要时可给高分。存在而无用途、职责错位或调用不明时才扣分。

### F. 鲁棒性与安全性（12 分）

| ID | 子项 | 满分 | 评价重点 |
|---|---|---:|---|
| F1 | 输入与边界验证 | 3 | 空输入、错误格式、规模和边界条件是否考虑 |
| F2 | 错误可操作性 | 3 | 失败信息、恢复建议和责任归属是否清楚 |
| F3 | 高风险保护 | 3 | 破坏性、外部变更或高成本操作是否确认、限界和可停止 |
| F4 | 权限与敏感信息 | 1 | 涉及凭证、隐私或权限时是否最小化暴露和说明 |
| F5 | 副作用与恢复 | 2 | 重试、幂等、回滚、降级或部分失败是否与风险匹配 |

F4、F5 可在确实没有敏感信息或外部副作用时标为 `N/A`。F3 对纯只读 Skill 可依据其明确边界评分，而非机械判为不适用。

### G. 渐进式披露与上下文效率（8 分）

| ID | 子项 | 满分 | 评价重点 |
|---|---|---:|---|
| G1 | 主体聚焦 | 3 | `SKILL.md` 保留所有任务共享的目的、流程和约束 |
| G2 | 条件资料拆分 | 2 | 大段、模式专用或条件性资料按需读取 |
| G3 | 脚本和资产使用 | 2 | 确定性逻辑与交付素材放在适合的位置 |
| G4 | 重复与孤儿资源 | 1 | 没有无意义复制、不可发现引用或无人使用文件 |

文件行数只是线索，不是评分目标。短但缺少关键规则的主体不能因“省上下文”得高分。

### H. 验证、兼容与维护（10 分）

| ID | 子项 | 满分 | 评价重点 |
|---|---|---:|---|
| H1 | 结构和引用验证 | 2 | 元数据可解析，路径和核心引用存在 |
| H2 | 脚本与依赖验证 | 2 | 适用时验证脚本参数、输出、错误和依赖 |
| H3 | 行为测试覆盖 | 3 | 正向、负向、异常、分支和不同规模请求得到测试 |
| H4 | 目标环境与可移植性 | 2 | 权限、联网、工具、平台差异和路径假设得到说明 |
| H5 | 可维护性 | 1 | 结构自包含，更新入口、版本或反馈方式与分发需求匹配 |

H2 在没有脚本和可执行依赖时可为 `N/A`。H5 中的版本、许可证只在发布或团队分发确实需要时评价。

## 4. `N/A` 处理

只有条件项确实不适用时才使用 `N/A`，并写明原因。核心项目如输入、输出、完成条件、主流程和结果验证不能为了避免扣分而标记为 `N/A`。

当维度内存在 `N/A`：

```text
维度得分 = 维度满分 × Σ(适用项满分 × 评级 ÷ 4) ÷ Σ(适用项满分)
```

这样会在该维度内重新分配权重，而不是把不适用项按零分处理。

## 5. 关键质量门禁

| 门禁 | 通过条件 | 失败判定 |
|---|---|---|
| G0 结构有效 | 主 `SKILL.md` 存在，必需元数据可解析 | 无法被正常发现或加载 |
| G1 核心路径完整 | 从有效输入到主要交付存在可执行路径 | 核心任务无法完成或必须猜测关键步骤 |
| G2 核心依赖可获得 | 核心引用、脚本和能力存在或有明确获取条件 | 必经路径引用缺失或环境不可能满足 |
| G3 风险受控 | 高风险和不可逆操作有授权、范围、停止或恢复保护 | 存在无保护的重大副作用 |
| G4 完成可验证 | 有可观察完成条件和实际检查动作 | 无法判断交付是否正确完成 |
| G5 触发可区分 | 描述能说明适用时机并与相近请求区分 | 严重误触发或漏触发风险 |

每个门禁状态只能是：

- **通过**：有直接证据支持，未发现关键缺口。
- **有条件通过**：核心可用，但受已声明的环境、输入或验证限制。
- **未通过**：存在阻断问题。
- **未验证**：现有证据不足以判断。

总门禁结论由最严重状态决定：存在“未通过”即整体未通过；否则存在关键“未验证”则整体未验证；否则存在“有条件通过”则整体有条件通过；其余为通过。

门禁不修改算术总分，但决定可用性结论。报告可以出现“设计得分较高，但因 G3 未通过而不建议执行”，不能让总分冲淡重大风险。

## 6. 证据置信度

对每个适用评分项给出证据系数：

| 系数 | 证据状态 |
|---:|---|
| 1.00 | 结构事实有直接文件证据；或行为主张有目标环境运行证据 |
| 0.75 | 指令有直接证据，但预期行为未经真实运行验证 |
| 0.50 | 多项事实支持的强推断 |
| 0.25 | 只有局部证据或可能解释 |
| 0.00 | 未知、缺失或冲突尚未解决 |

根据评分项权重计算：

```text
证据置信度 = Σ(适用项满分 × 证据系数) ÷ Σ(适用项满分) × 100%
```

对纯结构事实，完整静态文件可以达到 1.00；对“能够正确触发”“脚本可运行”“结果可靠”等行为主张，没有测试时最高使用 0.75。

置信度等级：

| 范围 | 等级 | 解释 |
|---:|---|---|
| 85～100% | 高 | 文件和行为证据充分，关键结论可复核 |
| 65～84% | 中 | 静态证据较完整，但部分行为未经验证 |
| 40～64% | 低 | 材料不完整或较多结论依赖推断 |
| 0～39% | 很低 | 不足以支持稳定总评 |

## 7. 总分等级

| 总分 | 等级 | 解释 |
|---:|---|---|
| 90～100 | 卓越设计 | 完整、克制、可作为高质量设计案例 |
| 80～89.5 | 良好设计 | 核心可靠，存在少量局部改进空间 |
| 70～79.5 | 基本可用 | 可以完成任务，但有明显短板 |
| 60～69.5 | 待完善 | 框架存在，稳定性、边界或验证不足 |
| 40～59.5 | 高风险 | 多个核心环节缺失，不建议直接使用 |
| 0～39.5 | 尚未成立 | 尚未形成有效、可执行的 Skill |

只有同时满足以下条件时，才可在结论中称为“卓越且经过验证”：

- 总分至少 90；
- 所有门禁通过；
- 证据置信度至少 85%；
- 有目标环境中的正向、负向和异常输入验证。

其他静态高分只能称为“设计质量高”。

## 8. 评分证据和扣分规则

每个维度至少列出：

| 子项 | 评级 | 换算得分 | 证据 | 判断与扣分理由 | 改进方向 |
|---|---:|---:|---|---|---|

遵守以下规则：

- 同一缺陷可以影响不同能力，但不要在语义相同的子项中重复扣分。
- 冲突既降低相关项评分，也降低证据置信度；说明冲突双方。
- 没有测试记录时，降低 H3 和行为证据置信度，不臆测测试失败。
- 缺失核心引用时同时反映在 E3、H1 或 G2，但分别说明“架构”“验证”“阻断”的不同影响。
- 改进建议必须对应已观察到的缺口，不为追求满分增加无用文件、流程或示例。
- 如果现有材料不足以稳定评分，可以报告暂定分数区间，并把总门禁标为“未验证”。

## 9. 总评写法

总评先呈现：

```text
设计质量：<分数>/100（<等级>）
质量门禁：<通过/有条件通过/未通过/未验证>
证据置信度：<百分比>（<等级>）
分析类型：<局部静态/完整静态/深度验证>
```

然后用不超过三条分别说明：

- 得分最高的设计能力及其证据；
- 最影响可靠性的缺口；
- 优先级最高、能改变关键结果的改进。

不要用一个总分替代这些解释。
